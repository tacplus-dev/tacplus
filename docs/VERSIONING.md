# Versioning and release policy

Decided 2026-10-15. This binds releases, the images, the fix looper and every
consumer of tacplus.

## Versions

tacplus releases are `MAJOR.MINOR.PATCH` git tags `vMAJOR.MINOR.PATCH`
(`.github/workflows/release.yml` builds the binaries from the tag).

- **A patch is fixes only.** A new feature, a new annotation, a new generated
  surface or a changed generated surface never goes into a patch. A patch
  changes behaviour only where the previous behaviour was a defect.
- **Features come in on a minor.** Anything a consumer would have to learn
  about lands in `MAJOR.MINOR+1.0`.
- **A major is a breaking change** to what consumers already generate against.
  Generated code is regenerated by its consumers; there is no deprecation
  window (a window is hand-maintained compatibility). The major says so.

## What consumers pin

A consumer declares a **floor** and pins an **exact release**
(tacplus-dev/roadmap: decisions/deterministic-builds-2026-10-27.md):

- The floor, `tacplus: "2.1"` in `tacplus.yaml`, is the oldest `MAJOR.MINOR`
  whose features it uses. It is never a patch.
- The pin, `tacplus.lock` beside it, is the exact `MAJOR.MINOR.PATCH` its
  builds run and the build image they run in, by digest. A build fetches
  exactly that binary, checks it against the release's `checksums.txt`, and
  never resolves "newest": the same commit builds the same way, whoever or
  whatever starts it, and whenever.

Moving to a newer patch is a commit (`tacplus pin`, then commit
`tacplus.lock`), never something a build does. Every patch of a line must be
safe to take without reading the notes, because a patch is fixes only, so a
pin is moved to its line's newest patch as a matter of course, never kept on a
known defect.

## What fleets pin

A fleet pins each service it runs the same way, by **release line**
(tacplus#180; docs/USER.md, Fleet Build). `fleet.yaml` states the intent,
`version: "0.4"`, and `tacplus fleet build` resolves it to that line's highest
released `v0.4.PATCH` tag of the service's repo, pre-releases excluded, and to
the image that release published. `fleet.lock` records the result: the exact
version, its commit and the image digest. A service names a pre-release only
explicitly (`version: "0.4.3-rc.1"`), never a patch, and never a branch: a
service without `version` is refused.

Re-locking (running the build again) takes new patches of the stated lines;
moving to a new minor is a `fleet.yaml` change, and `tacplus fleet build
--check` says which services have a newer patch or minor. Services are `0.x`
until SeaBeam's launch (2026-12-01), so a minor may break; `1.0.0` comes at
launch. Each service's release (its tags and image) is its own repository's.

## Backports

Every fix is made on `main` first. It is then backported to **every minor
released within the last twelve months**, as its own patch release of that
minor. A minor older than a year is out of support: it gets no patches, and
a consumer still on it upgrades.

Each supported minor has a branch `release/MAJOR.MINOR`, cut at its `.0` tag
(or at its first good patch). A patch release is a tag on that branch. The
branch is protected: changes land only by pull request.

Supported today: `release/2.0` through `release/2.7`, one per minor (2.0 was
cut at `v2.0.1`; 2.0.0 published images but its release build failed, so
2.0.1 is the first usable 2.0 release). `tacplus pin` and `tacplus upgrade`
both take a line's newest patch. The fix looper opens one pull
request against `main` and one against each supported release branch; the
release-branch pull request carries only the fix and its test.

## Images

There is no tacplus image: tacplus is a binary, published with each release
(`tacplus-X-Y-Z-<os>-<arch>` and `checksums.txt`). The images are the
toolchains (tacplus-dev/roadmap: decisions/tacplus-images-2026-10-27.md).
`build` is `FROM base`:

| image | contents | rebuilt when |
|---|---|---|
| `ghcr.io/tacplus-dev/tacplus/base` | OS and every SDK tacplus is built and tested with: Go, Java (JDK, Maven), Rust, Python, Node (TypeScript), Swift, .NET | weekly from main (`latest`), nightly for each supported line from its release branch (`X.Y`) when it has something new, or when an SDK pin changes |
| `ghcr.io/tacplus-dev/tacplus/build` | `base` plus every tool: protoc and every plugin, grpcio-tools, Kani, JBMC and OpenJML, cargo-fuzz and its nightly Rust, cargo-zigbuild and zig (the fleet builder's `rust:` client recipe), just, the docker CLI, gcloud. Its `tacplus` is `images/tacplus.sh`, which runs the release the repository pins. What a repository's build runs in (generate, compile, test, fuzz, verify), and what tacplus's own gates run in: CI, the nightly gates, `just gates-container` | every release (one image per line, built fresh), nightly for each supported line from its release branch when it has something new, and when a tool pin changes |

`ghcr.io/tacplus-dev/tacplus/tacplus` is deprecated: its tags up to the 2.5
line stay as they are, and it is never pushed again.

Tags on the `build` image:

| tag | meaning |
|---|---|
| `2.1.3` | the image of that release, immutable: a second push of it is refused |
| `2.1` | the newest 2.1.x image, rebuilt nightly from `release/2.1`, so it may move without a new 2.1.x; a convenience for people, never a pin: a build uses the digest in its `tacplus.lock`, and a CI image is pinned by a dated or `X.Y.Z` tag |
| `2` | the newest 2.x |
| `latest` | the newest release, or main's image when main rebuilt it |
| `<yyyymmdd>-<sha>` | every build of it, immutable: a line's nightly rebuild publishes one only when it has something new |

Releases are cut on several lines at once (a 2.0.x patch after 2.3.x), so a
floating tag moves only when the release is the newest it covers: `2.0.11`
cut after `2.3.1` moves `2.0` and leaves `2` and `latest` alone.
`scripts/images-tags.sh` decides; a pre-release gets only its own tag. A
release image is built with its line (`TACPLUS_LINE=X.Y`), and its `tacplus`
refuses a repository pinned to another line. A release job runs in
`build:X.Y` of its own line, never in `build:latest`.
The GitHub release is marked Latest by the same rule: only the newest
release of the newest line (`scripts/release-latest.sh`); a patch on an older
line is published with `--latest=false`, never taking Latest from the newest
line by being published last (#337).

A line's images are rebuilt from its own branch (#283) every night it has
something new (#966), so they take every Debian security fix (`apt-get
upgrade`) the night after it is published, without waiting for a patch. The
scheduled run on `main` dispatches `images.yml` on each supported
`release/X.Y` (a minor released within the last twelve months): every line
weekly, and on the other nights a line `scripts/images-line-stale.sh` finds
something new for: images/ changed on its branch, an upstream image its
Dockerfiles start from updated, or a Debian package to upgrade in its
`build:X.Y`, since its last successful line rebuild. A line with nothing new
is not rebuilt, so its dated tags (`build:<yyyymmdd>-<sha7>`, immutable) only
appear when there is a new package set; the run's summary names each line's
verdict, and the line's run names its digest. A repository's CI pins a dated
(or `X.Y.Z`) tag, never the floating `build:X.Y`, which moves under it
(tacplus-dev/roadmap: decisions/security-gates-ship-only-2026-11-23.md). That run
builds `base` and `build` from the branch and pushes `base:X.Y`, `build:X.Y`
and the dated tag, nothing else: never `latest`, `main`, `X` or any `X.Y.Z`.
So `build:X.Y` (and `base:X.Y`) may move without a new `X.Y.Z`; every
`X.Y.Z` stays the image of that release, immutable. A dispatch on a release
branch is always such a line rebuild. A patch tag builds its `build` fresh
(`apt-get upgrade`), from its line's `base:X.Y`, never re-tagging the line's
older image. Every run upgrades the OS packages (#369): the `apt-get upgrade`
layer depends on the run's id (`APT_REFRESH`), so the build cache cannot hand
back an older run's layer, and a run whose index lacks linux/amd64 or
linux/arm64, or holds an image created before the run started, fails before
any `X.Y.Z` or floating tag moves (`scripts/images-check-index.sh`).

A Debian package advisory (a DSA) is fixed in `base`, not in `build` alone
(#757). Both images run `apt-get upgrade`, so rebuilding `build` alone clears
the build images but leaves `base:latest` and every `base:X.Y` on the old
package until the scheduled run. The Nightly security sweep scans `base:latest`
and fails `main` until then. The fix is:

1. Dispatch `images.yml` on `main` with `rebuild: base`. This moves
   `base:latest` and `build:latest`.
2. Dispatch it on each supported `release/X.Y`. This is a line rebuild: it
   moves `base:X.Y` and `build:X.Y`.
3. If a release's pin must take the fix, tag a patch on that line afterwards.
   Its `build:X.Y.Z` starts from the fresh `base:X.Y`.

A patch tag alone does not do this: it rebuilds only `build` (#711 left
`base` behind this way). The fix is done when `trivy image --severity
HIGH,CRITICAL --ignore-unfixed` reports nothing on `base:latest`, each
`base:X.Y`, `build:latest` and each `build:X.Y`. A dispatch needs `actions:
write` on the repository. Without it, a change to `images/base.Dockerfile`
landed on `main` rebuilds `base:latest`. On a line, the same change backported
to `release/X.Y` rebuilds `base:X.Y` with the line's next patch tag: a tag
rebuilds `base` when its definition changed since the line's previous tag. A
push to a release branch runs no image build. Otherwise the lines wait for the
nightly run.

The definitions are `images/base.Dockerfile` and `images/build.Dockerfile`.
Their Debian packages are `images/base.packages` and `images/build.packages`
(#554): an image carries those, Debian's base system (Essential, Priority
required or important) and what they depend on, nothing else.
`images/packages-check.sh`, shipped as `tacplus-packages-check`, is the last
step of each image's build and fails it on any other package (OpenEXR, with
CRITICAL CVEs, came in through `buildpack-deps`, which `rust:X-trixie` is
built on; `base` now starts from `rust:X-slim-trixie`). A package an image
needs goes into its list, never in through the image it starts from.
`images/smoke.sh` ships in the build image as `tacplus-smoke` and runs inside
every pushed image, and `images/smoke-pipeline.sh` generates, tests, verifies
and fuzzes a pinned repository in it through its `tacplus`.
`.github/workflows/images.yml` builds and pushes them for linux/amd64 and
linux/arm64: `build` on every release tag and when its file changed on
`main`, `base` when its file changed (or weekly, or on demand), and both
nightly on each supported release line with something new. Each run
writes the build image's digest to its summary. `just images` builds the set
natively for one machine.

The build image builds images itself, with `tacplus-image-build`: rootless
BuildKit, with no host Docker socket in the container (#315;
tacplus-dev/roadmap: decisions/builds-in-containers-2026-11-03.md).
images.yml builds base and build with it in `build:latest`, and falls back to
buildx on the runner, once, while `build:latest` predates the tool.
The build cache comes from the build's configuration (`TACPLUS_CACHE_REGISTRY`,
`TACPLUS_CACHE_BUCKET`, `TACPLUS_CACHE_DIR`; [install](INSTALL.md#image-builds-and-the-build-cache)),
never from the image. With none configured, the build is cold.
`images/cache-determinism.sh`, which `just images` runs in the image it builds,
requires that compilers and an image built cold and then warm give the same
verdict and the same digests.

The first release tag is `v2.0.0`: the public tacplus-dev/tacplus line is a
new major over the private v1.2.x line it was forked from (new module path,
regenerated consumers).
