# Versioning and release policy

Decided 2026-10-15. This binds releases, the images, the fix looper and every
consumer of tacplus.

## Versions

tacplus releases are `MAJOR.MINOR.PATCH` git tags `vMAJOR.MINOR.PATCH`
(`.github/workflows/release.yml` builds the binaries from the tag).

- **A patch is fixes only.** A new feature, a new annotation, a new generated
  surface or a changed generated surface never goes into a patch. A patch
  changes behaviour only where the previous behaviour was a defect.
- **Features come in on a minor.** Anything a consumer would have to learn
  about lands in `MAJOR.MINOR+1.0`.
- **A major is a breaking change** to what consumers already generate against.
  Generated code is regenerated by its consumers; there is no deprecation
  window (a window is hand-maintained compatibility). The major says so.

## What consumers pin

A consumer pins **major and minor**, never patch. `2.1` means "the newest
2.1.x", and every 2.1.x must be safe to take without reading the notes,
because a patch is fixes only. Pinning a patch is allowed for reproducing a
problem, never for staying on a known defect.

## Backports

Every fix is made on `main` first. It is then backported to **every minor
released within the last twelve months**, as its own patch release of that
minor. A minor older than a year is out of support: it gets no patches, and
a consumer still on it upgrades.

Each supported minor has a branch `release/MAJOR.MINOR`, cut at its `.0` tag.
A patch release is a tag on that branch. The fix looper opens one pull
request against `main` and one against each supported release branch; the
release-branch pull request carries only the fix and its test.

## Images

Three images, each `FROM` the one before it so only the changed layer is
rebuilt and pulled:

| image | contents | rebuilt when |
|---|---|---|
| `ghcr.io/tacplus-dev/tacplus/base` | OS, protoc, and the language runtimes (Go, JDK, Rust, Node, Swift) | on a schedule, or when a runtime pin changes |
| `ghcr.io/tacplus-dev/tacplus/build` | `base` plus every build-time tool: the protoc plugins, Maven, the cargo plugins, just, jq, the docker CLI, gcloud | when a tool pin changes |
| `ghcr.io/tacplus-dev/tacplus/tacplus` | exactly what `tacplus build` shells out to: git, protoc and the plugins, Node (protoc-gen-es), gofmt, and the binary; a few hundred MB; what a generate step pulls | every push to `main` and every release |
| `ghcr.io/tacplus-dev/tacplus/tacplus-build` | `build` plus the tacplus binary, for a build that generates and compiles in one container | every push to `main` and every release |

Tags on the `tacplus` and `tacplus-build` images follow the version policy
(both always carry the same binary at the same tag):

| tag | meaning |
|---|---|
| `2.1.3` | that release, immutable |
| `2.1` | the newest 2.1.x patch (what a consumer pins) |
| `2` | the newest 2.x |
| `latest` | the newest release |
| `main-<sha>` | an unreleased build of `main` |

`base` and `build` are tagged `<yyyymmdd>-<sha>` and `latest`.

The definitions are `images/base.Dockerfile`, `images/build.Dockerfile` and
`images/tacplus.Dockerfile` (targets `slim` and `full`); `images/smoke.sh` is
run inside every pushed image as `tacplus-smoke`. `.github/workflows/images.yml` builds and pushes them for
linux/amd64 and linux/arm64 on every push to `main` and every release tag,
rebuilding `base` and `build` only when their file changed (or weekly for
`base`, or on demand). `just images` builds the set natively for one machine.
The first release tag is `v2.0.0`: the public tacplus-dev/tacplus line is a
new major over the private v1.2.x line it was forked from (new module path,
regenerated consumers).
